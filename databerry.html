Technical project · financial workflows

DataBerry — Gmail Finance Manager

Invoices, billing notices and other financial records often arrive in email threads, attachments and service-specific messages. Finding the right item later can mean switching between inbox searches, document folders and separate records. DataBerry explores how these pieces could be brought together in a single interface for searching, organizing, reviewing and exporting financial information.

I explored multiple implementations of the application, with the aim of connecting an interactive web interface, a server-side API and structured database storage. The project demonstrates architecture exploration and full-stack problem-solving; it is not presented as a finished, successfully deployed product.

The challenge: connecting scattered financial information

Financial correspondence is not always easy to manage as a coherent record. Relevant information may be distributed across messages and documents, while users need a practical way to locate items, inspect associated records and export data for further use. The design challenge was to create a consistent workspace without implying that every part of the workflow could already run reliably from end to end.

From interface concepts to a full-stack architecture

The latest reference implementation documents a React and TypeScript front end built with Vite, a Node.js and Express back end, and a PostgreSQL database accessed through Drizzle ORM. Tailwind CSS and shadcn/ui are listed among the interface technologies. Google Cloud Run was selected as the target hosting environment, with Google Cloud Build intended for the build pipeline.

This architecture separates the user-facing experience from server-side operations and persistent data storage. It also provides a concrete structure for exploring how search, document management, settings and export functions could work together. The project history includes approximately fifteen repositories exploring variants of the same initiative; these represent iterations, not fifteen separate projects.

Functional scope

Across the documented designs and implementations, the functional scope includes:

  • Searching for and organizing financial emails.
  • Managing documents associated with email-based financial information.
  • Presenting dashboards and monitoring views.
  • Maintaining structured records and application settings.
  • Exporting selected data in CSV format.
  • Exploring integrations with Gmail and other Google services.

The maturity of these elements varies across versions. This list describes the documented scope of the initiative, not a claim that every feature is operational in the latest repository.

Implementation and deployment status

The latest reference repository documents the intended full-stack architecture, but the application was not successfully deployed to Google Cloud after repeated Cloud Build failures. The cause has not been established. Screenshots and interface designs provide evidence of visual structure and navigation, but they do not establish successful end-to-end operation or verified performance.

For that reason, DataBerry is best described as an advanced development and architecture-exploration project. The available sources do not establish that the complete workflow is running in production, nor do they provide validated usage, accuracy, processing-volume or time-saving metrics.

What the project demonstrates

  • Breaking a broad information-management problem into front-end, back-end and database components.
  • Exploring a modern web stack using React, TypeScript, Node.js, Express and PostgreSQL.
  • Designing around search, structured records, document handling and data export.
  • Iterating across implementation variants while keeping the initiative’s scope distinct from its individual repositories.
  • Reporting technical progress transparently, including unresolved deployment issues and features that still require validation.

The takeaway

DataBerry explores how financial information scattered across email and documents could be organized through a unified, data-backed web application. Its strongest evidence is the architecture and problem-solving work—not a claim of successful deployment or fully validated functionality.
